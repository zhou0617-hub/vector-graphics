## 三、代码修改规范

### 3.1 输出格式（最重要）

用户需要通过**复制粘贴**把 AI 的输出变成文件内容。所以：

| 场景 | 正确格式 |
|---|---|
| **写进 md 文件的文档内容** | 用**四条反引号**包裹的**纯 Markdown**，不混脚本、不混操作说明 |
| **要在 PowerShell 执行的命令** | 用三条反引号包裹的 **powershell 代码块** |
| **要写进代码文件的内容** | 用三条反引号包裹对应语言的代码块 |

**四条反引号的作用**：防止内容里的 ` ``` ` 三反引号提前截断代码块。

**用户明确要求**：写 md 文件内容时，必须用四条反引号包裹，内部是纯 Markdown，不要嵌入 PowerShell 或 Python 脚本，不要混操作说明。

### 3.2 PowerShell 脚本陷阱

**陷阱 1：BOM 问题**

PowerShell 5.1 的 `Set-Content -Encoding UTF8` 和 `Out-File -Encoding UTF8` 会写入 BOM（`EF BB BF`）。Python 解释器读到 BOM 会报 `SyntaxError: invalid non-printable character U+FEFF`。

**正确写法**：

```powershell
$content = @'
文件内容
'@

$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($FILE, $content, $utf8NoBom)
```

**错误写法**（会产生 BOM）：

```powershell
Set-Content -Path $FILE -Value $content -Encoding UTF8
$content | Out-File -FilePath $FILE -Encoding UTF8
```

**陷阱 2：here-string 容易出错**

`@'...'@` 里如果有 `@'` 或 `'@` 出现在行首会提前结束。同时，here-string 内容很长时容易粘贴不全。

**建议**：超过 30 行的文件内容，改用以下方式之一：

- 让用户直接在 VSCode 里新建文件粘贴
- 用 Python 脚本写（Python 的三引号字符串没这些问题）
- 分多次小段修改

**陷阱 3：curl.exe 传 JSON 丢引号**

```powershell
# 错误：PowerShell 会剥离 JSON 里的双引号
curl.exe -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -d '{"email":"111@qq.com","password":"111111"}'
```

**正确写法**（用 PowerShell 原生 `Invoke-RestMethod`）：

```powershell
$body = @{ email = "111@qq.com"; password = "111111" } | ConvertTo-Json
$resp = Invoke-RestMethod -Uri "http://localhost:8080/api/auth/login" -Method Post -ContentType "application/json" -Body $body
```

multipart 上传（`-F`）仍可用 `curl.exe`，字段值不含引号没问题。

**陷阱 4：路径含括号**

`frontend/src/app/(main)/...` 里的 `(main)` 会被 PowerShell 解析为参数。

**正确写法**：用 `-LiteralPath`：

```powershell
Get-ChildItem -LiteralPath "$ROOT\frontend\src\app\(main)\tools" -File
```

**陷阱 5：中文乱码**

读取 Java / Python 文件时加 `-Encoding UTF8`：

```powershell
Get-Content "path\to\file.java" -Encoding UTF8
```

### 3.3 Java 代码规范

- 分层：controller / service / repository / entity / dto / converter
- DTO 用 Lombok `@Data`
- Service 方法返回 DTO，**不直接返回实体**（避免泄露 userId 等内部字段）
- 异常用 `BusinessException`，全局处理器统一转换
- 数据库迁移用 Flyway，**不手动 ALTER TABLE**

### 3.4 Python 代码规范

- 用 `pathlib.Path`，不硬编码路径分隔符
- 类型注解必写
- 用 `pydantic-settings` 读配置
- 深度学习引擎注意 GPU / CPU 自动检测
- **绝不引入 BOM**

### 3.5 TypeScript / React 规范

- 组件 PascalCase，文件名 kebab-case
- 客户端组件显式 `'use client'`
- API 调用统一走 `lib/api/client.ts`
- 状态管理用 Zustand，服务端状态用 TanStack Query

### 3.6 数据库迁移

改动表结构必须新建迁移脚本：

1. 在 `backend/src/main/resources/db/migration/` 下建 `V{N}__{描述}.sql`
2. 版本号递增
3. 重启后端，Flyway 自动执行
4. **不改已执行过的脚本**（会 checksum 报错）

## 四、沟通规范

### 4.1 输出结构

每次回复按以下结构：

1. **判断**：当前问题是什么
2. **方案**：要做什么，为什么，影响范围
3. **执行**：代码 / 命令（按 3.1 规范包裹）
4. **验证**：怎么确认成功
5. **下一步**：接下来可以做什么

### 4.2 不要做

- 不要一次给 5 个方案让用户选，先给最推荐的
- 不要假设用户已执行上一步，每步都先确认输出
- 不要在长脚本里嵌多个语言（PowerShell 里嵌 Python 里嵌 Markdown）
- 不要用 `Set-Content -Encoding UTF8` 写 Python / Java 文件

### 4.3 要做

- 修改文件前**先读原文件**，确认实际内容再改
- 大改动前**先备份**（`Copy-Item xxx xxx.bak`）
- 涉及数据库的操作**先看表结构**
- 用户报错时**先看日志**再猜原因
- 每完成一个功能**同步更新 md 文档**
